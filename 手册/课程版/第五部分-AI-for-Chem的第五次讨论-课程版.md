## 5.1 发展：从回答问题到推进任务

### 5.1.1 先区分模型、对话与智能体

李冲以自己早期使用 ChatGPT 辅助写作的经历引入发展过程（26:15—29:18）。当时最直接的体验是可以自然对话、生成文字，但想让它读很多论文并模仿写作，仍受资料输入、上下文长度和结果可靠性限制。

吴冬的笔记把三个词分开：LLM 是理解和生成语言的模型；ChatBot 是通过对话与用户交互的应用形式；Agent 则围绕目标组织行动，选择工具、执行步骤，并根据结果继续处理。杨涵在笔记中把变化归纳为：交付单位从一轮回答变成一个任务，人的工作转向定目标、给边界、审结果，瓶颈也扩展到上下文、工具与验收。

**整理补充：这三个词描述的层次不同。** 一个聊天界面也可以连接工具并运行 Agent；一个 Agent 可以只用一个模型，也可以调用多个模型。判断时可以看它在这个任务中实际完成了什么：只是解释做法，还是读取材料、执行操作、检查结果并交付文件。

吴冬笔记中的例子是整理十篇论文。只返回一个整理模板，人与工具之间的搬运和检查仍由人完成；若系统能读取论文、找到段落、整理表格、注明出处并生成文件，它就在推进更多实际步骤。这里描述的是具备相应工具与权限的系统能力，不是对所有聊天产品的统一划分。

### 5.1.2 工具调用怎样把文字连接到操作

李冲用计算器说明早期纯文本作答与外部计算的区别，并接着介绍 Function Calling、工作流和后来的 Agent（28:26—30:16、34:10—38:28）。

**整理补充：一次工具调用可以理解为以下过程：**

1. 程序告诉模型有哪些工具可用，以及各工具需要哪些参数。
2. 模型根据任务生成结构化的调用请求，例如读取某文件或计算某组数据。
3. 外部程序按权限执行，把实际结果或错误信息返回。
4. 模型读取结果，决定回答、补充操作或调整步骤。

因此，模型输出“我要计算”，与计算程序已经执行，是两个不同状态。Agent 把这个往返组织成循环，才有机会持续完成较长任务。迪力笔记特别提醒，复杂任务可能在跑偏后不断强化错误，最后交付一个外观完整的结果；验收要检查产物与依据。

工作流（workflow）是把步骤及其衔接组织起来，例如依次读取、提取、去重、输出。现场李冲把工作流形容为已经过去的热点（38:28 左右）。**技术校正：热点变化可以作为个人观察保留，工作流仍是组织任务的方法；固定步骤与模型动态决策也可以组合使用。** 多 Agent 是一种分工方式，不是所有 Agent 的必备条件。

### 5.1.4 上下文与记忆解决什么问题

李冲早期想输入大量论文的例子，引出了上下文与 token（27:26—28:26）。补充视频《Agent、Skill、Harness啥意思？》也用连续规划旅行解释：系统需要把相关对话、规则和工具结果交给模型，模型才有依据继续。

**整理补充：上下文是模型当前处理时能看到的材料。** 它可以包括用户提问、历史对话、文件片段和工具结果，但总长度有限。系统可以通过检索、摘要和文件记录组织这些材料；保存到文件的经验，也要在后续被正确读取，才能影响当前回答。

现场把早期上下文说成“16K token，大约数万汉字”。**技术校正：具体窗口随模型版本而变；token 通常译作词元，不能固定换算为某个汉字数。** 摘要可能遗漏条件，保存记忆也不等于模型参数已经改变。后文关于长期记忆和 Skills 的讨论，应沿用这个区别。

## 5.2 依据：Agent 怎样检索资料、核查回答

### 5.2.1 RAG 的基本思路是把资料带进回答

李冲把 RAG 的动机讲得很直接：希望模型利用我们指定的材料、较新的资料和未公开文档回答，而不是只依靠训练中形成的知识（30:16—34:10）。他举出 ima、NotebookLM 等知识库应用作为理解入口。

RAG（Retrieval-Augmented Generation，检索增强生成）的基本过程是：**提出问题→检索相关材料→把材料与问题一起交给模型→依据材料生成回答。** 常见文档知识库会先解析文件、切成片段并建立索引，查询时取回相关部分。吴冬用“先翻资料再回答”解释，迪力进一步强调材料切分、检索和证据组织会影响最后的效果。

**技术校正：现场把幻觉主要归因于词语的数学接近关系，是帮助理解的简化。** 生成错误还可能来自知识不足、问题歧义、资料缺失、检索失配和推理错误等。RAG 给回答增加外部依据，有助于减少部分错误；实际效果取决于取得的材料与生成过程，不能写成已经消除了幻觉。

### 5.2.2 知识库、网页与本地文件怎样配合

| 资料入口 | 材料中的用法 | 实际要检查什么 |
|---|---|---|
| 知识库 | 导入论文、笔记或实验规程，再按问题检索 | 文件是否完整、版本与日期是否正确、是否保留来源位置 |
| 联网搜索 | 查新论文、模型说明、产品与套餐规则 | 打开原始页面，确认发布者、日期和正文，不能只抄搜索摘要 |
| 本地文件 | 在指定文件夹查 PDF、Word、表格或代码 | 是否读对文件、表格与图注是否完整、扫描件识别有无错误 |
| 接入的专业系统 | 迪力笔记举出文献管理器、代码仓库等 | 接口实际返回什么，是否有权限，条目能否回到原始记录 |

李冲补充，本地检索也可以直接匹配字符，不必每次都建向量库（37:49—38:28）。**整理补充：关键词检索适合精确的名称、编号和数值；语义检索适合寻找意思相近但措辞不同的段落。** 具体系统可以组合使用，检索不只等于向量匹配。

MCP（Model Context Protocol）在这里负责连接应用与外部数据、工具。它与 Function Calling 处在不同环节：前者约定接入方式，后者涉及模型如何表达工具调用请求。支持协议只是取得资料的通道，资料仍需核查。迪力笔记把专业系统称为“最可靠”，宜改为“通常更便于管理来源、版本与权限”，不能仅凭接入形式保证内容正确。

### 5.2.3 科研回答需要把结论与条件一起取回

吴冬笔记给出一个教学例子：询问聚合物 P1 的发射峰，应先确认测的是溶液、薄膜还是粉末，再记录峰位、单位和页码图号。笔记中的 520 nm 是假设数值，不是本组实验结果。

迪力把这一要求进一步联系到 AIE 数据：量子产率、荧光增强倍数、IC50 都依赖条件。只召回一个结果句，可能把不同溶剂、浓度或光照条件下的数值拼成不可比的表格。其课前要求是“结论必须与条件同召回”，每条结论能够回到 DOI。

**整理补充：一次可回查的提取至少应交代四件事：研究对象、结果与单位、有关条件、来源位置。** 具体字段随问题调整。例如 IC50 还要明确细胞与处理条件；光谱数据要区分样品状态和测量条件。DOI 帮助定位论文，页码、图表号和原文片段帮助定位证据，两者各有作用。

这承接了上一部分的可靠数据问题，但本次没有共同完成一条真实记录的“提取—核对—存档”演示。因此，已经有了方法要求，尚不能记成已经建立了可用的化学数据库。

### 5.2.4 自动核查怎样帮助人检查

袁桂萍的课前笔记介绍了多轮搜索、生成者与评审者分工、运行代码、模型裁判及自然语言推断（NLI）等方法。NLI 在这里指判断一段证据是否支持另一句话；这些属于笔记中的技术展开，现场没有逐一演示。

迪力把检查归纳为四问：是否需要查、查到的是否相关、证据是否足够、回答是否得到证据支持。吴冬的版本更适合直接使用：

1. 从哪里看到的？给出可打开的出处。
2. 原文哪句话或哪张图支持这个判断？核对对象和含义。
3. 条件是否一致？核对样品、单位、实验条件与日期。

**整理补充：多一个模型复核，可以增加检查机会；代码成功运行，可以核验一部分计算或文件处理。** 二者都需要明确标准：多个模型可能沿用同一错误来源，程序也可能正确执行了错误的科学假设。没有证据时标为未确认，来源冲突时保留各自条件，比强行合并成确定答案更有用。

袁桂萍笔记还把私有知识库与安全直接关联。**技术校正：文件在本地存放，并不能据此推断内容不出本机。** 检索片段若发给远端模型，仍发生了外部传输；应结合实际部署与数据政策判断，接入和隐私问题见本章后面的讨论。

## 5.3 Skills：怎样复用专业方法

### 5.3.1 吴冬的阅读方法先于技能文件

吴冬把 Skill 理解为方法论与工作流的结合，并详细讲了自己的论文阅读习惯（21:05—25:39）：先看前言和研究思路图，了解背景、现状、不足、作者的问题与解决方案，形成一页总结；再按自己的兴趣标红、标蓝和批注。作为聚合物方向研究者，他还关心最后的应用图，追问材料应用的原理、实验如何操作、效果怎样。

他随后澄清，自己常用的是聊天中的固定要求与上下文，未必真的写了一个 Skill 文件。李冲回应，这套稳定流程可以封装成 Skill。

**本章保留这个区别：已经在使用固定方法，与已经完成技能包，是两件事。** 吴冬的贡献在于把自己要看的内容说得具体，并让 AI 的输出进入自己的批注和判断流程。不能因为使用了 AI，就把后续阅读与判断也记作自动完成。

### 5.3.2 Skill 保存什么，怎样按需使用

李冲演示了用于 cover letter 的 Skill，其中包含写作要求、参考示例和格式（50:14—51:57）。他建议把过去认可的例子交给工具，要求总结为可复用方法，再持续修改。袁桂萍追问 Markdown 文件如何生成、能否多提供参考，得到的回应是可以让工具起草，也可以手动调整。

**整理补充：按 [Agent Skills 规范](https://agentskills.io/specification)，技能包的核心是带名称、描述与正文说明的 `SKILL.md`，还可以附脚本、参考资料和模板。** 支持这一机制的应用先识别用途，任务匹配后再读取方法和所需资源。这种按需展开有助于组织上下文，实际识别和执行效果还取决于应用实现。

| 内容 | 在一个科研 Skill 中的作用 |
|---|---|
| 适用任务与输入 | 说清何时使用，需要正文、SI 还是数据表 |
| 执行步骤 | 规定读取、提取、核对和输出的顺序 |
| 参考与模板 | 提供格式、例子和专业标准 |
| 工具或脚本 | 执行格式检查、去重或计算等明确操作 |
| 交付与失败处理 | 说明怎样验收，缺资料、读不清或执行失败时怎样报告 |

现场把 Skill 类比为“高级的 prompt”（51:57 左右），有助于理解它仍然依赖清楚的指令。**技术校正：普通提示词也能保存、共享和版本管理；Skill 的特点在于把方法及资源按应用支持的形式组织和调用。** 它不会仅凭封装就变成保证执行的程序，也不需要通过重新训练模型才能使用。

补充视频《普通人如何用好Skill》强调先完成一件事，再把满意的流程沉淀下来。这与现场演示一致；视频中“自动触发永久生效”的说法需收窄为“在支持并正确加载它的环境中复用”。

## 5.4 市场：模型、客户端与 Harness 怎样区分

### 5.4.1 杨涵的问题把各层关系连起来

杨涵使用 VS Code 中的 Cline 接入模型服务生成简历，随后问：“Agent 到底是这个 VS Code，还是我们用的那个火山引擎？”（58:12—01:00:49）。袁桂萍也反复追问充值的服务、客户端与实际调用的模型是什么关系（42:46—46:27、01:15:22—01:17:01）。

李冲解释，Agent 是一整套系统：模型提供能力，Harness 把环境、工具与执行流程组织起来。火山引擎提供模型服务，用户通过客户端接入。吴冬用租房、租算力的类比帮助理解。

**整理补充：用杨涵报告的路线，可以这样分层：**

| 层次 | 在这条路线中是什么 | 主要作用 |
|---|---|---|
| 编辑器 | VS Code | 展示与管理项目文件，承载扩展 |
| Agent 扩展 | Cline | 组织对话、文件操作、命令执行与任务推进 |
| 模型服务平台 | 火山引擎中实际接入的服务 | 接收请求，提供可调用的模型服务并管理用量 |
| 具体模型 | 配置中选择的模型标识 | 处理上下文，生成回答或工具调用请求 |
| 接入配置 | 服务地址、密钥、模型标识等 | 使扩展连接到相应服务 |

本表解释的是成员所述关系，没有读取其配置验证具体型号。服务平台可以托管不同来源的模型；平台品牌不能直接当作模型名称。普通模型 API 也通常是在购买推理服务，不能等同于已经租到一台可任意操作的 GPU。

### 5.4.2 IDE、终端和桌面端是交互入口

杨涵介绍自己熟悉的豆包，认为它适合自然语言交流，也能在她所用环境中读取文件并在获准后操作；这是个人使用体验（18:02—20:20）。李冲随后演示编辑器侧栏、在 PowerShell 或 CMD 中启动的终端工具，以及具有按钮和页面的桌面客户端（38:55—42:38）。

- **编辑器／IDE 形态**：在项目文件与代码旁边交流，便于查看修改。VS Code 严格说是可扩展编辑器，配合扩展可承担相应开发工作。
- **终端形态**：在命令行窗口启动工具并交互，常见于编程与自动化工作。
- **桌面或网页形态**：以窗口、按钮、预览和对话承载任务，具体文件与工具能力由产品提供。

**技术校正：终端也有界面，只是以文本为主；在终端启动 Agent 后，同样可以用自然语言交代任务。** 使用这种入口不要求先掌握完整编程语言，但需要逐步理解工作目录、操作范围和输出。图形界面是否更占内存，取决于实现和任务，本次没有同条件测量，现场的占用比例不作通用结论。

李冲和吴冬还比较网页端的便利与本地操作的差别（56:43—58:01）：网页便于多设备使用，本地 Agent 可以直接处理工作目录。**整理补充：实际区别应检查工具与权限。** 网页应用也可能处理上传文件或连接外部服务；桌面应用也可能把内容发送到云端。不能只凭“网页／本地客户端”推断执行位置和数据流向。

### 5.4.3 Harness 是让模型持续工作的配套结构

李冲在开场和回答杨涵时用马具类比 Harness：模型要进入工作环境，需要一套工具、状态、规则与执行安排（10:34—11:37、59:12—01:00:49）。补充视频也把上下文、权限边界、结果反馈与修正放在这一层。

**整理补充：Harness 可理解为围绕模型运行的工程配套。** 它既帮助模型取得上下文、使用工具、保存任务状态，也安排执行循环、权限和检查。现场的马鞭比喻强调约束；理解时还要保留“提供可工作的环境”这一面。`Agent = Model + Harness` 可以作为本章的概念简写，不是严格的行业定义。

李冲介绍 DeepSeek Harness 时强调“一切皆插件”，并把它与其他客户端作比较（46:27—47:37）。迪力的课前笔记则怀疑是否存在这一正式产品。**整理核查：本次重新查看的 [DeepSeek 官方页面](https://www.deepseek.com/zh/harness/)明确展示预览版、桌面下载、开源入口与插件能力，因此产品存在可以确认。** 迪力原先的存疑结论需要更新，保留其“以官方发布为准”的核验方法。

官方页面也展示了现成工作入口，不能把“可替换组件”进一步概括为“什么都没有，全部需要自己搭建”。插件架构与开箱体验可以并存。本章不据旧对比分析追记具体首发月份。

李冲还介绍了一个侧重本地持续记忆的产品，转写音近 Hermes，但现有材料不足以确认（47:37—48:56）。本章保留其所描述的做法：把纠错经验写下来，供下次读取；同时也保留他与吴冬的顾虑——记录过多或内容错误，可能干扰后续任务，记忆仍需要维护。

## 5.5 接入与付费：API、密钥与套餐

### 5.5.1 袁桂萍讲清了请求怎样来回

袁桂萍用手机应用调用远端模型说明 API，把 API Key 比作身份与权限凭证，并描述了地址、请求数据、服务器处理和返回结果的过程（11:54—16:42）。李冲后来结合 Python 包演示同一关系（44:59—46:27）。

**整理补充：API 是程序之间约定的调用接口。** 在常见模型服务中，客户端把模型名、消息和参数按约定格式发给服务地址，附上有效凭证；服务端校验后运行任务，再返回文字、工具调用请求或错误。Python 包或 SDK 是帮助程序组织这些请求的工具包，模型通常仍在服务端运行。

API Key 是访问凭证，关联权限与用量；拿到它不等于不限额或无需付费。成员笔记提醒不要把密钥放到公开代码、截图或共享文档，迪力还强调不提交到 Git，泄露后撤销。补充视频《AI还要付费？》以“外卖系统”解释跨应用调用，可帮助入门，但免费与收费是服务商规则，API 本身不等于必须收费。

配置第三方工具时常见三项是 **Base URL（服务基础地址）、API Key、模型标识**。地址、凭证与支持的模型必须匹配相应服务；同名模型在不同服务中也可能有不同标识。现有录音没有足够配置细节，本章不据转写补写成员实际使用的地址或型号。

### 5.5.2 Coding Plan 在现场被纠正了含义

袁桂萍最初把 Coding Plan 解释为 Agent 动手前生成的编程计划。李冲当场指出不符题意；她随后读到笔记后半部分“固定月费＋额度池”的解释，得到确认（13:42—13:52、15:00—16:18）。李冲在 38:55 左右再次对齐了这两个含义。

本次第五问中的 **Coding Plan 指面向指定编程或 Agent 工具的订阅套餐**。任务执行前写出的 plan 则是工作计划。两种说法都可能出现在产品语境中，应根据所问的是“怎样做任务”还是“怎样接入和计费”判断。

这个例子也回应了依据问题：笔记里的文字看起来通顺，却可能回答了另一个含义。现场把问题具体化后，才发现同一份笔记前后用了两套定义。

### 5.5.3 三类付费方式怎样比较

| 方式 | 买到什么 | 需要核对的限制 |
|---|---|---|
| 网页／桌面订阅 | 某个应用或账号计划包含的功能与额度 | 哪些入口可用、共享哪些额度、是否另含开发工具权益 |
| API 按量付费 | 按服务规则计量的模型与相关调用 | 模型单价、输入输出、缓存及额外工具费用，用量上限 |
| Coding Plan | 指定工具、模型和用途下的订阅额度 | 支持的工具、地址和密钥类型、短期窗口与总量、允许的用途 |

吴冬笔记提醒，三者可能捆绑，也可能分别出售。买聊天会员不自动得到通用 API 余额；有套餐密钥也不表示可以挪作任意批量程序使用。李冲笔记中的“API 极贵、Coding Plan 极便宜”需要改为按具体任务与用量比较，不能作为普遍价格关系。

袁桂萍提到当天下午购买的 9.9 元服务和短时间达到限额，随后仍在辨认自己买的是什么（15:00—16:42、01:14:26—01:17:01）。本章保留这是成员的实际困惑；缺少订单与后台记录，不能判定具体套餐、完整限制或当时被限额的原因。

### 5.5.4 一次提问为什么会消耗很多额度

吴冬在笔记中用打印店作比：一次印一页与一次印一本书，不能都按“一次”比较价格。Agent 为完成一个任务，可能反复发送上下文、读取工具结果和继续调用模型，所以用户发了一条消息，后台不一定只调用一次。

**整理补充：比较费用时先确认计量单位。** 有的按 token，有的按请求或积分；还可能区分模型、缓存命中和工具调用。需要比较的是完成同一合格任务的总费用、耗时与失败后重试，而不是只比一次调用的报价。

课前五人分别提供了不同案例，细节保存在原笔记中：李冲查 OpenAI 订阅，杨涵查智谱积分，袁桂萍查 DeepSeek 按量服务，迪力查阿里云百炼，吴冬查 Kimi 新旧会员规则。多数案例未在现场完整展开，不能把五家笔记当作现场共同核查过的套餐表。

整理时重查了两个与额度理解直接有关的官方案例（核对日期：2026 年 10 月 22 日）：

- [阿里云 Coding Plan](https://help.aliyun.com/en/model-studio/coding-plan)：页面列出 Pro 每月 200 元，以及每 5 小时 6,000、每周 45,000、每月 90,000 次请求等多重上限；支持具体模型白名单和指定工具。请求额度不等同于用户提问次数，购买前还须看当前页面和账号条件。
- [Kimi 会员额度规则](https://www.kimi.com/help/membership/membership-update-rules)：区分会员共享额度与 Kimi Code 的使用限额，保留新旧套餐差异。不能把“5 小时”理解为只能坐在电脑前工作五小时，也不能把短期限制恢复理解为整个月额度重新发放。

**本次未逐项重查其他笔记中的价格、折扣、积分公式和型号。** 原数值可作为当时的准备材料回看，使用或购买前应重新核对。也不能把一家服务的窗口恢复机制推广给全部厂商。

### 5.5.5 数据是否用于训练，要看实际政策

开场李冲认为个人订阅即使关闭训练选项，数据仍会用于训练，而按量 API 完全不会；吴冬、袁桂萍继续追问科研材料和保密项目（08:47—10:34）。这是本次需要重点校正的一段，不能直接作为通用事实。

**技术校正：收费方式、训练用途、数据留存与外部传输应分别判断。** 以本次核查的 [OpenAI API 数据控制说明](https://developers.openai.com/api/docs/guides/your-data)为例，API 数据默认不用于训练，用户主动选择共享的情况除外；与此同时，相关服务仍可能存在安全日志或应用状态留存。因此“不会训练”和“完全不保存”也不能混写。

现场关于个人产品“关掉选项也一定训练”的断言没有提供依据，本章不予确认；更不能据此断言所有厂商政策相同。实际使用应核对具体产品、账号类型、设置、服务商及接入的第三方。API 也不因价格较高就天然有统一的隐私保障。

李冲把一般科研与国家机密作区分，吴冬提醒保密项目可能要求本地部署。**整理补充：普通未发表科研材料也可能涉及保密义务；是否允许上传应按项目和机构要求决定。** “本地客户端”“本地资料库”和“模型在本地运行”要分别确认。本章保留成员的风险意识，同时撤下没有证据支持的确定性结论。

## 5.8 本章小结

1. **从回答到行动，需要完整的执行关系。** 模型、工具、上下文、执行循环与权限共同影响任务结果；界面长什么样不能单独决定它是不是 Agent。
2. **检索的价值在于取得可用依据。** 科研结论要连同对象、单位、条件和来源位置保存；有引用还需要核对内容是否支持判断。
3. **Skill 从稳定的工作方法中产生。** 吴冬的阅读习惯、李冲的形式检查，以及其他成员的任务设想，展示了不同的复用对象；封装后仍需试用、检查和修订。
4. **模型、服务平台与客户端要分层辨认。** 杨涵关于 VS Code、Cline 和火山引擎的追问，揭示了接入中的核心困惑；具体模型与能力应从配置和实际操作确认。
5. **套餐限制需要按计量规则理解。** 用户一次提问可以触发多次模型调用，月费、短期窗口和总量限制应一起看；训练用途与数据留存另查政策。
6. **个人经验与核查结论分别保存。** 时间线口误、DeepSeek Harness 存疑和隐私断言得到不同程度的校正；模型偏好和市场推测不改写成测评结论。
7. **学习开始转向可检查的实践。** 本次已出现简历生成与接入经历，尚缺全员产物验收；下一步倾向从 SMILES 和分子特征进入性质预测。
