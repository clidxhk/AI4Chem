## 引言

上一章介绍了机器怎样从数据中建立预测关系，以及如何评价模型。
假设你要整理十篇论文。
你可以请 AI 告诉你该提取哪些信息，再自己打开文件、摘录内容并制作表格。
也可以把论文交给一个能读取文件和生成表格的应用，让它按要求整理，遇到缺页时继续查找，最后交付结果供你核对。

两种做法都用到了 AI，差别在于实际操作由谁完成。
本章从这个差别出发，看看 AI 怎样从陪人聊天，走向帮助人完成一项工作。

本章沿五个问题展开：

1. **发展**：从聊天到 Agent，任务的执行方式发生了什么变化？
2. **依据**：Agent 怎样取得资料，回答怎样与来源对应？
3. **Skills**：怎样把常用的专业方法保存下来，供以后复用？
4. **市场**：模型家族、服务平台和 Agent 产品怎样区分与选择？
5. **接入与付费**：工具怎样连接模型服务，费用怎样计算？

## 5.1 发展：从回答问题到推进任务

### 5.1.1 从用过的 ChatGPT 说起

打开 ChatGPT，输入一句“帮我把这段论文摘要翻译成中文”，很快就能得到一段回答。
你还可以接着说“再通俗一点”“保留专业术语”“压缩到一百字”，它会结合前面的对话继续修改。
这种用日常语言交流的方式，是许多人最初认识 AI 的入口。

**ChatGPT 是 OpenAI 提供的 AI 应用，早期以聊天机器人的形式走进大众视野。**
ChatBot 就是“聊天机器人”：用户发消息，软件以对话的方式回应。
早期 ChatGPT 最吸引人的地方，是同一个聊天窗口就能用来问知识、翻译、写作和修改代码。

支撑这些能力的核心，是**大语言模型（Large Language Model，LLM）**。
它在训练时接触大量文本，学习语言表达与内容之间的关系；使用时，根据你提供的问题、材料和前面的对话生成回答。
GPT 是这类模型的一个系列，ChatGPT 则把模型能力做成了人们能够直接使用的产品。

例如，让它解释“为什么某种分子聚集后发光增强”，模型可以组织一段说明；把一段英文摘要贴进去，它可以据此翻译、概括或改写。
**聊天窗口让人提出要求，大语言模型负责处理语言、生成内容。**
后来，开发者又为这样的应用接上了搜索、文件处理、计算和操作软件的工具，AI 能参与的工作就逐渐增多了。

### 5.1.2 从回答一个问题，到完成一项工作

整理十篇论文时，单靠对话，你往往需要自己打开论文、复制文字，再把 AI 的回答粘贴到表格里。
要让软件多接手一些工作，就需要把“读文件、提取信息、整理表格”这些操作也接起来。

**Workflow（工作流）把一项工作拆成步骤，按照预先设计的顺序和条件运行。**
例如，可以安排这样的文献整理流程：

读取论文 → 逐篇提取研究问题与主要结论 → 记录出处 → 汇总成表格。

每一步接收前一步的结果，再把自己的结果交给后一步。
其中，提取结论可以交给大语言模型，读取 PDF 和生成表格则由相应工具完成。
流程搭好以后，同一套做法就能反复处理不同批次的论文。

实际工作还会出现需要临时判断的情况。
例如，一篇论文是扫描件，直接读取不到文字，就需要换成文字识别；某条结论缺少出处，就需要回到论文补查。
这时，可以让模型根据当前结果决定下一步，调用合适的工具，再查看结果是否满足要求。

**围绕一个目标，能够选择行动、使用工具，并根据结果继续推进工作的 AI 系统，称为 Agent（智能体）。**
**Workflow 把常见步骤安排好，Agent 根据执行情况选择下一步；两者可以结合在同一套应用里。**
对于使用者，操作也可以很简单：交代目标、提供材料，在需要时补充说明，并检查最后的交付结果。

![Agent 中模型提出行动、环境返回反馈并继续执行或停止的循环](https://clidxhk.github.io/AI4Chem/手册/通用版/图片/第五部分/agent-loop.png)

*图 5-1　Agent 的执行循环。来源：[Anthropic，Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，原图。*

图中的 Human 是使用者，LLM Call 是模型处理当前任务，Environment 是文件、程序和其他工具所在的环境。
沿箭头看，系统采取行动（Action），接收结果（Feedback），再决定继续还是停止（Stop）。

### 5.1.3 从聊天机器人到日常助手，经历了哪些变化

**更早的基础：让程序围绕目标行动。**

智能体研究已有长期积累。
至少在 1990 年代，研究者就在系统讨论：程序怎样感知环境、选择行动、与其他程序协作，以及怎样完成给定目标。[Wooldridge 与 Jennings，1995](https://doi.org/10.1017/S0269888900008122)
这为后来把语言模型、工具和任务执行结合起来提供了思想基础。

**2022 年：自然语言对话成为大众入口，语言模型也开始与行动结合。**

2022 年 11 月 30 日，ChatGPT 发布。
人们用几句日常语言就能让它解释问题、起草文字或修改内容，使用 AI 的门槛明显降低。[ChatGPT 发布说明](https://openai.com/index/chatgpt/)

同年公开的一项研究探索了另一件事：让模型先判断需要查什么，再借助工具取得信息，读到结果后继续判断下一步。
例如，遇到材料不足的问题，可以先搜索，阅读搜索结果，再决定怎样回答。
这种把分析与行动交替进行的思路，成为后来许多语言模型 Agent 的重要基础。[2022 年相关研究](https://arxiv.org/abs/2210.03629)

**2023 年：接上资料和工具，让模型能查、能算。**

人们很快希望 AI 能查到新资料、读取自己的文件，并用计算工具处理数字。
开发者让更多语言模型应用能够查找资料、读取文件和使用外部工具。
2023 年 6 月，OpenAI 发布了支持这种配合的功能：模型可以按约定提出操作请求，由应用执行，再把结果交回来。[工具调用功能发布说明](https://openai.com/index/function-calling-and-other-api-updates/)

例如，回答一项分子性质问题时，系统可以先查数据库，再把查到的记录交给模型解释；处理一份实验表格时，可以运行计算程序，再根据计算结果生成说明。
资料检索与工具执行，使 AI 能把外部信息和实际操作接进对话。

**2023—2024 年：Workflow 把多步工作接起来，Dify 等平台让流程变得可搭建。**

单次查找或计算只能完成工作中的一小步。
要反复整理文献、处理表格或生成报告，就需要把多个步骤组织起来，并安排好信息怎样在步骤之间传递。

Dify 是用于搭建 AI 应用的平台。
2024 年 4 月，它推出可视化 Workflow：使用者可以在画布上连接代表不同步骤的方块，安排模型处理、资料查找、工具执行，以及遇到不同情况时该走哪一步。[Dify Workflow 发布说明](https://dify.ai/blog/dify-ai-workflow)
例如，把“接收论文—提取字段—检查缺项—生成表格”连成一个可重复运行的应用，就不必每次都在聊天窗口逐条交代。

这类平台把原本需要编写许多程序才能接通的流程，变成较直观的搭建过程。
组织一项 AI 工作，开始从反复输入要求，走向设计整套处理流程。

**同一时期：多个 Agent 开始分工协作。**

任务进一步变长后，开发者又尝试把不同部分交给不同的 Agent：一个检索资料，一个整理内容，另一个检查遗漏，最后汇总结果。
**多 Agent 系统就是让多个 Agent 交换信息、分工或协作，共同推进一项任务。**

2023 年的 AutoGen 提供了一套帮助开发者搭建多 Agent 应用的软件框架。
它允许开发者定义不同 Agent 的职责，以及它们怎样相互发送消息、调用工具和接收人的反馈。[Microsoft Research，AutoGen](https://www.microsoft.com/en-us/research/blog/autogen-enabling-next-generation-large-language-model-applications/)
在科研任务中，这种思路可以用于分头阅读不同论文，也可以把整理与复核交给不同的角色，再汇成一份交付物。

**2024 年：扩展到软件界面，并让工具更容易接入。**

有些工作发生在网页和桌面软件中，需要查看屏幕、填写内容和点击按钮。
2024 年 10 月，Anthropic 推出 computer use 公开测试版，让模型能通过工具查看屏幕并操作鼠标和键盘，扩展了 AI 能参与的工作范围。[computer use 公告](https://www.anthropic.com/news/3-5-models-and-computer-use)

同年 11 月，Anthropic 又提出连接资料和工具的共同规范，让开发者更容易把已有系统接进 AI 应用。[工具连接规范发布公告](https://www.anthropic.com/news/model-context-protocol)
一个方向扩展了操作方式，另一个方向减少了连接不同工具时的重复开发。

**2025 年：Claude Code、Manus 等产品让用户直接交代整项任务。**

2025 年 2 月推出的 Claude Code，把 Agent 带进实际编程环境。
用户提出修改要求后，它可以读取项目文件、修改代码、运行测试，再根据报错继续调整。[Claude Code 发布公告](https://www.anthropic.com/news/claude-3-7-sonnet)

2025 年 3 月上线的 Manus，则把通用 Agent 带到更广泛的用户面前。
用户可以交代资料调研、数据分析或网站制作等目标，由产品组织多步执行，交付报告、图表或网页。
这种使用方式使普通用户也能直接体验“给出目标，软件继续把工作往下做”。[Manus 上线回顾](https://stripe.com/customers/manus)、[Manus 早期应用总结](https://manus.im/blog/what-we-saw-in-the-past-three-months-and-what-we-see-in-the-future)

同年 7 月，Manus 发布 Wide Research，把较大规模的资料收集任务拆开，由多个 Agent 并行处理，再汇总结果。
多 Agent 协作由开发框架中的组织方法，进一步成为用户可以直接使用的产品功能。[Wide Research 发布说明](https://manus.im/blog/introducing-wide-research)

**2025 年末—2026 年：OpenClaw 等个人 Agent 进入日常使用场景。**

OpenClaw 项目起步于 2025 年 11 月，在 2026 年 1 月采用 OpenClaw 名称时已受到广泛关注。
它可以部署在个人电脑或服务器上，并连接 WhatsApp、Telegram 等聊天工具。
配置完成后，用户可以在熟悉的聊天软件里交代任务，由助手调用接入的工具处理工作。[OpenClaw 项目介绍](https://openclaw.ai/blog/introducing-openclaw)

Manus 把多步执行做成可直接使用的服务，OpenClaw 则让个人助手进入用户已有的设备和交流入口。
Agent 的使用场景由编程和流程搭建，进一步扩展到资料整理、日常事务和个人工作。

从早期 ChatGPT 到这些产品，用户交给 AI 的内容逐渐从一个问题扩展为一项工作。
这些产品把模型、工具和执行过程整合起来，让使用者通过熟悉的对话方式安排更复杂的工作。

## 5.2 依据：先取得资料，再检查回答

### 5.2.1 模型怎样利用眼前的材料

在 ChatGPT 中问“这篇论文的主要结论是什么”，只给出这句话，模型还没有论文内容。
把摘要贴进去后，它才能围绕这段摘要回答；再补上结果部分和图注，它能利用的材料就更多了。

**上下文（Context）是模型在这一次处理时能够看到的全部材料。**
其中可以包括你的要求、应用带入的相关对话、论文文字，以及搜索或读取文件得到的结果。
例如，“用中文整理”“每条结论保留图号”是任务要求，读到的论文段落是作答依据；两者一起影响输出。

对话中说“把刚才的表格加一列”，应用需要把相关表格和前面的要求再次交给模型，它才能接着修改。
应用怎样选择、保留和补充这些材料，会影响连续工作的效果。

一次能够放入的材料有容量限制。
对很长的论文集，应用通常需要选择有关段落，或分批读取和处理。
因此，文件是否已经上传、其中哪些内容实际进入了本次处理，是需要分别了解的两件事。

### 5.2.2 从自己贴材料，到让应用先查资料

如果问题涉及刚发表的论文或个人实验记录，模型训练时未必接触过这些内容。
一种直接做法，是自己找到有关段落，连同问题一起发给它。
资料多起来以后，应用可以接手查找这一步。

例如，要问“这篇论文中 P1 的发射峰在哪里”，应用可以先在指定论文中查找 P1，读取附近的光谱说明与图注，再把这些内容交给模型组织回答。
**先检索相关资料，再让模型依据资料生成回答，这种做法称为检索增强生成（Retrieval-Augmented Generation，RAG）。**

整个过程可以分成四步：

1. 提出问题，并确定到哪些资料中查找。
2. 找到相关段落、表格或图注。
3. 把找到的材料与问题一起交给模型。
4. 生成回答，并保留支持回答的来源位置。

![用户提问后先检索相关文档，再交给语言模型生成回答](https://www.elastic.co/docs/solutions/images/elasticsearch-reference-rag-schema.svg)

*图 5-2　先查资料，再生成回答。来源：[Elastic，RAG system overview](https://www.elastic.co/docs/solutions/search/rag)，原图。*

沿图中的 1—4 看：用户提问（User query），检索系统 Elasticsearch 找到相关文档，语言模型（Language model）据此组织回答，最后返回结果（Response）。
上方两项分别控制怎样查找，以及回答应遵守哪些要求，例如保留出处。

前面说的“找到的材料”，就是在这一次处理中补入上下文的内容。
更新论文或实验记录后，应用可以检索新材料，供模型使用。
在这种做法中，新增资料保存在模型之外，使用时再取来阅读。

有些应用会先把一批论文整理成便于检索的资料集合，也就是常说的**知识库**。
它们通常先读取文件，将内容分段并记录位置，以便提问时找到有关部分。
RAG 的代表性论文发表于 2020 年，研究者当时已经在探索怎样把外部资料检索与语言模型生成结合起来。[原始论文](https://arxiv.org/abs/2005.11401)

检索效果取决于文件是否读完整、问题是否表达清楚，以及相关内容能否找到。
例如，表格与图注被拆开，可能使模型只看到数值而看不到条件。
因此，检查这种回答时，要同时看“找到了什么”与“怎样依据材料作答”。

### 5.2.3 知识库、网页和本地文件各有用处

| 资料入口 | 适合取得什么 | 怎样检查 |
|---|---|---|
| 已整理的知识库 | 论文、笔记、实验规程等已有材料 | 查看文件版本、完整性及原文位置是否保留 |
| 联网搜索 | 新论文、官方产品说明、更新后的规则 | 打开原始页面，核对发布者、日期和正文 |
| 本地文件 | 指定目录中的 PDF、Word、表格或代码 | 确认文件路径，检查表格、图注和识别文字 |
| 文献管理器等专业系统 | 条目、附件与结构化记录 | 回到原始条目或附件，核对来源与权限 |

知识库与本地文件可以重叠：本地文件可以先整理成便于检索的资料集合，也可以直接搜索和读取。
联网搜索取得的内容也可以再进入知识库。

**关键词检索**适合查找化合物编号、专有名称和精确数值。
**语义检索**关注意思是否相关，适合原文与问题用词不同的情况。
两种方法可以结合，用关键词定位，再读取附近段落和图表。

Agent 可以根据任务选择入口；第一轮信息不足时，再换关键词、补查文件或寻找原始来源。
RAG 提供“把资料带进回答”的方法，Agent 则可以组织检索、阅读、补查和输出的多步过程。

### 5.2.4 科研结论要连同测试条件取回

假设要问：“论文中的聚合物 P1 在什么波长发光？”
找到一个发射峰数值之后，还要确认 P1 的样品状态、溶剂、测量条件及对应图表。

若原文写的是“P1 在某溶剂中的发射峰为 520 nm”，答案就应保留该溶剂条件和来源位置。
这里的 520 nm 是教学假设。
读者据此能知道结果适用于哪一种测量，也能回到图谱核查。

**结果与条件一起提取，数据才有明确含义。**
量子产率、荧光增强倍数和细胞实验的 IC50 等尤其依赖条件；把不同条件下的数值放在一起时，需要先判断可比性。

| 要素 | 需要记录什么 | 对光谱例子的作用 |
|---|---|---|
| 研究对象 | 化合物或样品编号、状态 | 确认对应的是 P1 溶液、薄膜还是粉末 |
| 结果与单位 | 数值、单位、结果类型 | 区分发射峰位与激发波长等不同量 |
| 相关条件 | 影响当前结果含义的实验条件 | 记录溶剂、浓度及有关测量设置 |
| 来源位置 | DOI、页码、图表号或原文片段 | 定位论文，并在论文内找到支持证据 |

具体字段由研究问题决定。
提取细胞实验结果时，要进一步明确细胞、处理时间和光照等相关条件；不能把光谱字段机械搬过去。

这也承接了前几章的数据问题：取得资料只是开始，能追溯、能比较的记录才适合继续用于分析或建模。

### 5.2.5 核查回答需要逐条对齐证据

**判断一条回答有无依据，可以连续问三个问题：**

1. **从哪里看到的？** 给出能打开的论文、文件或官方页面。
2. **哪句话或哪张图支持这个判断？** 检查结论与原文是否对应。
3. **条件是否一致？** 核对样品、单位、实验条件与日期。

引用链接帮助定位材料，逐条对齐则帮助检查材料是否真的支持结论。
两篇论文结果不同时，可以先列出各自的样品和条件，再判断差异来自何处。
若现有材料不足，应标明缺少的依据，继续补查或保留为未确认。

自动核查可以承担一部分重复工作，例如把表格数值与原文比对，检查是否缺少出处，或运行计算核对单位换算。
也可以让另一个模型对照原文复核。

人工检查应优先关注关键结论、重要数字和容易混淆的条件。
多个模型可能沿用同一错误来源，成功运行的程序也可能执行了不合适的处理方法；核查标准仍需要研究者确定。

### 5.2.6 保存记录，让下次能够接着做

整理十篇论文，今天完成前五篇，明天还要接着处理。
如果只留下最终表格，应用可能不知道哪些论文已经核对、哪些数据仍待补查，也可能漏掉你中途补充的要求。

可以在任务过程中保存一份记录，写清已经处理的文件、尚未解决的问题，以及约定的输出格式。
下次继续时，应用先读取这份记录，再取得需要的论文，就有依据接着工作。

**记忆（Memory）是应用为以后使用而保存的信息。**
它可以是任务进度、你的长期偏好，或经过确认的方法；具体保存什么、放在哪里、什么时候读入，由应用设计和设置决定。

上下文是模型这一次实际看到的材料，记忆则是留待以后取用的记录。
**保存的记忆被再次读取并交给模型时，才会成为当次上下文的一部分。**
例如，进度文件可以保存全部十篇论文的处理状态，而本次只读入待处理的三篇和相关要求。

记录应准确、相关并保持更新。
压缩后的摘要适合帮助恢复进度，核对关键结论时仍应打开原文，查看完整条件与出处。

## 5.3 Skills：把专业方法变成可复用规程

### 5.3.1 先有稳定做法，再把它保存下来

阅读论文时，每个人都有关注重点。
有人先看前言和研究思路图，想知道科学问题与解决方案；有人更关心应用图，需要了解材料怎样使用、实验如何操作、效果如何。

如果每次都要求 AI 按同样顺序整理，就可以把这套做法写成规程。
**Skill（技能包）把一类任务的使用条件、执行方法、参考材料和输出要求组织起来，供支持它的应用复用。**

例如，“论文前言阅读笔记”可以固定回答：

1. 这项研究想解决什么问题？
2. 已有方法做到了什么程度？
3. 还存在哪些不足？
4. 作者提出了什么新办法？
5. 研究思路图怎样解释这项工作？

规程再要求保留重要化合物编号和图号，把关键判断对应到来源，区分作者的结论与阅读者的理解。
得到一页笔记后，研究者可以继续批注，并据此决定哪些实验和段落值得精读。

这样，专业方法来自实际工作的需要，AI 输出也进入了自己的阅读与判断流程。

### 5.3.2 技能包怎样组织与加载

技能包的核心是一份写给 Agent 的操作说明，记录它在什么情况下、应该怎样完成这类工作。
按 [Agent Skills 规范](https://agentskills.io/specification)，这份文件命名为 `SKILL.md`，其中写明名称、用途与具体步骤，还可以配上处理文件的小程序、参考资料和模板。

![技能说明文件的名称、用途、操作步骤和配套资料](https://clidxhk.github.io/AI4Chem/手册/通用版/图片/第五部分/skill-anatomy.jpg)

*图 5-3　一个真实的 Skill 文件怎样组织。来源：[Anthropic，Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)，原图。*

图中文件开头的 `name` 是技能名称，`description` 是用途简介，帮助应用判断什么时候使用它。
下方正文写具体做法，也可以指向配套文件；图中把 PDF 表单的详细操作放在 `forms.md` 里，需要处理表单时再读取。
科研阅读 Skill 可以采用同样结构，把用途写在前面，把阅读步骤、来源要求和输出模板放在正文及配套文件中。

支持该机制的应用可先识别用途，任务匹配时再读取步骤，执行到需要某项资源时继续加载。

这种**按需加载**把用途说明、操作方法和详细资源分开，帮助应用组织有限的上下文。
触发与使用方式要与具体应用匹配。

![应用先读技能简介，收到任务后读取操作说明，再按需读取配套文件](https://clidxhk.github.io/AI4Chem/手册/通用版/图片/第五部分/skill-context-loading.jpg)

*图 5-4　Skill 怎样逐步进入上下文。来源：[Anthropic，同上文](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)，原图中的 Claude 示例。*

从上往下看：先有各 Skill 的简短说明，用户提出 PDF 任务后，系统读取相应 `SKILL.md`，再按其中的引用读取 `forms.md`。
图中的 Tool use 表示实际读取文件，Tool result 表示读到的内容进入上下文；这里不需要重新训练模型。

从使用角度看，技能包需要讲清以下内容：

| 内容 | 应回答的问题 |
|---|---|
| 用途与输入 | 什么任务适用，需要哪些文件与信息？ |
| 执行步骤 | 先做什么，怎样提取和核对？ |
| 参考与模板 | 按什么标准判断，输出长什么样？ |
| 工具或脚本 | 哪些明确操作交给程序执行？ |
| 验收与失败处理 | 什么算完成，缺资料或报错时怎么办？ |

平时直接发给 AI 的任务要求，通常叫作提示词，也可以保存、共享和记录修改版本。
Skill 进一步把方法与资源组织成应用可识别、可按需调用的包，使同类任务更方便沿用统一做法。
执行后仍需检查产物，并根据失败情况修改规程。

### 5.3.3 从文献阅读走向不同科研任务

| 可复用任务 | 方法中需要固定的内容 | 合格产物怎样检查 |
|---|---|---|
| 论文阅读笔记 | 关注问题、篇幅、图号与来源要求 | 回原文核对关键判断，检查重要信息是否遗漏 |
| 文献综述与引用核验 | 检索范围、去重、主题整理与引用对应 | 每条主要结论能回到来源，检查是否混淆条件 |
| 参考文献与图号检查 | 当前期刊样式、正文与条目对应、图号顺序 | 对照指南与原文件核查，检查字段和编号是否完整 |
| AIE 文献跟踪 | 来源范围、筛选标准、去重记录与卡片格式 | 检查 DOI、条件与重复项，不足时按实际数量报告 |
| 光动力实验标准操作规程（SOP）整理 | 已认可的加样、光照、孵育与表征步骤 | 对照原规程核对条件和缺项，保留版本与修改依据 |

不同任务的验收标准不同。
为比较量子产率而整理的文献卡片，可以严格要求相关测试条件；只想了解研究思路时，筛选标准则可以有所调整。

实验 SOP 类 Skill 可以帮助准备、检查和记录规程。
实际控制仪器或执行实验，还要连接相应硬件与接口，并验证执行过程。

### 5.3.4 怎样从一次成功任务形成 Skill

可以先选一个经常重复、范围明确的任务，让 Agent 完成一次。
在过程中指出漏项、格式和判断问题，直到结果符合自己的标准，再要求把方法、例子与验收要求整理成技能包。

例如，先把一篇论文整理成满意的阅读笔记，再保存五问、来源标注与输出模板。
随后换一篇论文试用，检查这些要求能否继续适用。
遇到综述、缺页或没有研究思路图的材料时，要说明怎样调整，而不是强行填写。

**值得保存的是能重复使用、能判断好坏的方法。**
任务太宽时，可以先缩小范围，例如从“把整个手稿改好”收窄为“按指定指南检查参考文献格式，并列出问题与位置”。
格式检查有较明确的标准，研究叙事和科学论证则需要更多专业判断。

写作任务也可以规定结构，例如摘要先交代背景与挑战，再概括方法和结果。
结构帮助组织材料，工作结果与创新程度仍由原文证据支持；需要用实际文本判断质量。

如果希望每天自动执行文献跟踪，还要另外设置启动时间和运行条件。
Skill 保存做法，定时任务负责何时启动，执行记录则帮助检查是否成功。

## 5.4 市场：分清模型、服务与产品，再选择工具

### 5.4.1 从一个实际使用场景分清角色

假设你用 Cline 整理个人简历，并生成能在浏览器中打开的网页文件。
Cline 是可以安装在 VS Code 中的 Agent 扩展，VS Code 则是用来查看、编辑和管理项目文件的软件。
你在界面里提出要求，Cline 组织读取和修改文件，并向所连接的模型服务请求处理。

这项工作中，几个角色分别承担不同的事情：

| 角色 | 在这个例子中做什么 |
|---|---|
| 编辑器 VS Code | 展示文件，让你查看和修改内容 |
| Agent 应用 Cline | 安排读取、修改、运行与结果检查 |
| 模型服务平台 | 通过网络提供模型处理，管理账号和用量 |
| 具体模型 | 理解要求和材料，生成内容，判断下一步行动 |

**模型提供处理信息的能力，应用把这些能力组织成可以使用的工作过程。**
同一个应用可以支持不同模型，一个平台也可以提供多个厂商的模型。
因此，了解一套工具时，可以依次确认自己在用哪个应用、它连接哪家服务，以及实际选择了哪个模型。

### 5.4.2 编辑器、终端和桌面端是不同入口

**编辑器／IDE 形态**把 AI 交互放在项目文件旁边，便于查看代码与修改。
IDE 指集成开发环境；VS Code 是可扩展编辑器，安装扩展后可承担相应开发工作。

**终端形态**通过文本窗口启动和使用工具。
启动 Agent 后，通常也可以用自然语言交代任务；学习工作目录、文件路径和基本命令，有助于理解它在操作什么。

**桌面或网页形态**用窗口、按钮和预览承载任务。
适合哪种入口，取决于工作中更需要查看代码、处理文件、跨设备交流，还是预览成品。

这些形态可以在同一产品中并存。
应查看具体入口能读取哪些文件、调用哪些工具、在哪里执行，以及操作时需要哪些权限。

### 5.4.3 Model 与 Harness 怎样组成 Agent

**今天常见的 LLM Agent = Model（模型）＋ Harness（运行框架）。**
Model 负责理解要求、处理材料，并判断下一步做什么。
Harness 是围绕模型搭建的软件运行框架，负责连接工具、安排操作执行、记录进度，并把执行结果交回模型，支持它继续处理任务。[LangChain，The Anatomy of an Agent Harness](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

例如，整理文献时，模型判断扫描件需要文字识别，Harness 就把文件交给识别工具，再把识别结果交回模型；模型随后继续提取论文内容。
用工具打开文件、检索资料或运行计算，通常称为**工具调用**。
**我们实际使用的 Agent，就是模型与运行框架配合起来形成的整套工作系统。**

模型根据工具结果继续判断，系统再执行下一步，任务就形成了“判断—行动—再判断”的循环。
研究者在 2022 年提出的 ReAct 方法，探索的就是让语言模型交替进行分析和行动，并利用取得的结果继续处理问题。[ReAct 原始论文](https://arxiv.org/abs/2210.03629)

Harness 还组织上下文、任务状态、操作权限与执行反馈，使工作能够连续进行。
例如，文献处理到第五篇时程序报错，系统需要保留已处理记录、把错误返回，并避免重做或覆盖前面的结果。

同一个模型接入不同的 Harness，可以获得不同的工具和工作方式；同一套 Harness 也可以接入它支持的不同模型。[LangChain，On Agent Frameworks and Agent Observability](https://www.langchain.com/blog/on-agent-frameworks-and-agent-observability)
因此，选择 Agent 产品时，需要一起了解它使用什么模型，以及运行框架能组织哪些实际工作。[Anthropic，Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

![语言模型在应用中连接检索、工具和记忆等外部能力](https://clidxhk.github.io/AI4Chem/手册/通用版/图片/第五部分/augmented-llm.png)

*图 5-5　围绕模型连接外部能力。来源：[Anthropic，Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，原图中的 augmented LLM。*

绿色框是语言模型，下方的 Retrieval、Tools、Memory 分别表示检索、工具与记忆。
这些连线在实际系统中需要由应用及其配套结构实现，Harness 还要组织任务状态、权限和执行检查。
图中先看清“模型”和“外围能力”各在什么位置，就容易理解为什么只选一个模型，还不足以决定整套 Agent 怎样工作。

工具增多以后，应用还需要与不同资料系统和软件建立连接。
**MCP（Model Context Protocol，模型上下文协议）是一套共同的连接规范**，让支持它的 AI 应用能够按约定取得资料、发现和调用工具。
例如，文献管理系统提供相应连接后，Agent 应用就可以查询条目和读取允许访问的材料。[Anthropic，MCP 发布说明](https://www.anthropic.com/news/model-context-protocol)

Harness 既提供执行能力，也安排约束与检查。
使用者能否看见改动、收窄目录、停止任务和回查结果，会影响实际使用体验。

[DeepSeek Harness](https://www.deepseek.com/zh/harness/)是一个具体产品例子：官方页面提供预览版桌面入口，并以插件扩展工具、技能和界面。
插件是可按需添加的功能组件。
使用者可以通过桌面入口安排任务，再按需要添加插件。

### 5.4.4 国产模型家族怎样认识

模型家族通常包含不同型号，型号还可能面向不同输入、任务和部署条件。
初学时先认识名称与产品线，再根据具体版本比较能力。

| 家族 | 认识入口 | 查看具体型号时的重点 |
|---|---|---|
| [DeepSeek](https://www.deepseek.com/en/transparency/) | 语言模型及相关推理、工具使用能力 | 任务表现、服务速度、费用及是否允许所需用途 |
| [Qwen](https://qwen.ai/apiplatform) | 不同规模和任务类型的模型系列 | 支持什么材料、能否在自己的设备运行及使用条件 |
| [Kimi](https://www.kimi.com/) | 长资料、编程与知识工作相关模型和产品 | 长文件读取、来源保留与任务完成情况 |
| [GLM](https://docs.z.ai/guides/overview/quick-start) | 编程、知识处理和 Agent 相关模型 | 具体型号、工具使用与输出质量 |
| [Doubao](https://www.volcengine.com/product/doubao) | 日常应用及云平台上的多类模型服务 | 文本、图像等输入需求与实际可用功能 |
| [MiniMax](https://www.minimax.io/) | 语言、视频、语音与音乐等模型及产品 | 选择的是哪条产品线，以及它的具体任务 |
| [MiMo](https://mimo.xiaomi.com/) | 语言、图像等信息处理与工具使用相关模型 | 具体版本能力、部署要求和适用场景 |

能够处理文字、图像或声音等多种类型信息的模型，通常称为**多模态模型**。
查看具体版本时，要确认它能接收哪些材料、生成哪些结果；若希望在自己的设备运行，还要查看能否下载、设备要求及使用许可。

上述入口帮助认识产品线，没有提供统一条件下的性能排名。
模型规模、单次使用印象或家族名称，都不足以单独决定哪个版本最适合一项工作。

### 5.4.5 用实际任务判断产品是否合适

Trae、Qoder、Kimi Code、ZCode、WorkBuddy、DeepSeek Harness、MiniMax Code 等名称，可以作为进一步了解 Agent 产品的入口。
产品功能与入口会变化，比较时应确认具体版本和配置。

对化学研究者，先选择一个自己能够核查的小任务更有帮助。
例如，用相同的光谱表格，让不同工具读取数据、作图并交付图像与汇总表。

| 比较方面 | 可以怎样检查 |
|---|---|
| 材料读取 | 核对样品数、列名、单位和缺失值是否读对 |
| 执行情况 | 查看脚本是否实际运行，输出文件是否生成 |
| 专业处理 | 核对所用数据列、处理步骤、坐标与单位 |
| 修改与沟通 | 记录漏项、纠正次数，以及是否容易说明要求 |
| 成本与时间 | 记录达到合格结果的总费用与耗时 |

评测榜单可以提供候选范围，真实任务则帮助判断工具能否适应自己的材料与标准。
对某个任务形成的结论，应连同模型版本、服务方、工具配置与测试日期保存。

## 5.5 接入与付费：让应用调用模型服务

### 5.5.1 应用怎样向模型服务请求处理

在模型厂商的网页里聊天时，产品已经安排好了连接过程。
使用 Cline 这类可连接不同服务的应用时，则需要指定由哪家服务提供模型处理。

应用怎样把要求送过去，又怎样收回结果，需要双方遵守共同的约定。
**API（Application Programming Interface，应用程序编程接口）就是程序之间约定的调用方式。**
模型服务的 API 会说明请求发到哪里、需要提交哪些信息，以及结果怎样返回。

一次调用大致经过以下过程：

1. 应用准备问题、相关材料，以及要使用的模型名称。
2. 应用把请求发到服务地址，并提供访问凭证。
3. 服务校验后，让相应模型处理，再返回结果或错误信息。
4. 应用显示结果，或根据返回内容继续处理任务。

通过这种连接，模型能力就能进入编辑器、表格工具或自己的程序。
连续处理多份文件时，应用可以逐次准备材料、收取结果并保存。

### 5.5.2 地址、密钥与模型标识怎样配合

配置第三方工具时，常见三个项目：

| 配置 | 含义 | 怎样核对 |
|---|---|---|
| Base URL | 服务的基础地址 | 对照服务商为当前产品或套餐提供的接入文档 |
| API Key | 用于验证访问权限的一串字符，关联账号与用量 | 确认来自相应账号和服务，在安全的配置位置填写 |
| 模型标识 | 请求使用的具体模型名称 | 对照该服务当前支持的模型列表 |

地址、凭证与模型标识需要匹配同一个服务配置。
同名家族在不同服务中可能使用不同标识，套餐专用地址也可能与普通按量接口不同。

**API Key 同时关系到权限和账单，应按私密凭证保存。**
不要把它放进公开代码、Git 提交、截图或共享文档；发生泄露时应撤销并重新配置。
部分官方应用通过账号登录取得使用权限，用户无需手动填写密钥。

![Cline 配置页中分别填写服务地址、被遮蔽的 API Key 和具体模型标识](https://clidxhk.github.io/AI4Chem/手册/通用版/图片/第五部分/cline-provider-settings.png)

*图 5-6　客户端怎样连接模型服务。来源：[d.run 官方文档，在 VSCode 和 Cline 中使用](https://docs.d.run/models/user-guides/cline-in-vscode)，原图；旧版界面示例。*

图中显示的是 Cline 的设置页；Base URL 指向 d.run 的服务，Model ID 则选择该服务提供的 `public/deepseek-r1`。
API Key 是访问该服务的凭证，图中已用圆点遮蔽。
API Provider 中的 OpenAI Compatible 表示采用兼容的接口格式；实际服务方要看地址，实际模型要看 Model ID。
这几个字段分别对应应用、服务与模型之间的连接关系，填写时应使用自己所选服务当前提供的配置。

### 5.5.3 订阅、按量与 Coding Plan 各买什么

| 方式 | 通常获得什么 | 购买前看什么 |
|---|---|---|
| 网页／桌面订阅 | 某应用或账号计划中的功能和额度 | 支持的入口、功能、共享额度与附带权益 |
| API 按量付费 | 按实际使用量计费的服务 | 处理输入与生成输出的单价、重复材料的计费规则、工具费用与用量限制 |
| Coding Plan | 在指定编程或 Agent 工具中使用的订阅额度 | 工具与模型清单、专用地址、额度和允许用途 |

三类服务可以分别售卖，也可以在同一个会员体系中组合提供。
购买前应确认所需工具能否使用这份权益，以及是否需要额外费用。

**Coding Plan 是面向指定编程或 Agent 工具的付费套餐。**
通常按订阅周期提供一定额度，具体可用工具和额度计算方式由服务方规定。

比较价格时，应结合真实用量。
按量付费的单价、固定订阅的限制和超额处理方式共同决定总成本，需要结合每次处理的材料长度、任务次数和套餐限制判断。

### 5.5.4 一次提问怎样变成多次消耗

一次用户消息可能触发多次模型调用：先读取文件，再生成脚本，运行后读到错误，再修改并继续。
每次调用还可能携带此前的相关内容和工具结果。

每次调用处理的文字有长有短：一句问题和一整篇论文，带来的工作量相差很大。
服务通常用 **Token（词元）** 计量模型处理的内容。
文字会被切分成一串片段，每个片段算一个 Token；切分结果随语言、文本和模型使用的切分方式变化，不能固定换算成汉字数或英文单词数。

**输入 Token** 对应交给模型的要求、资料和相关历史等内容；**输出 Token** 对应模型生成的内容。
按文字处理量计费的服务，会根据有关输入和输出用量计算费用。
同样问一句话，附带一篇长论文，通常就会比只附一段摘要带入更多输入。

Token 也用于表示一次能容纳多少上下文。
长任务中，应用可以保留必要要求、总结已有进展，并在需要时重新读取原文件，使有限容量用于当前工作。

因此，**用户提问次数、模型调用次数与 Token 用量，是不同计量对象。**
就像去打印店，一次印一页与一次印一本书，不能只按“一次”比较费用。

套餐还可能同时设置短期窗口、每周或每月的使用限制。
短期窗口控制集中使用量，总量限制控制整个周期的用量；两者会共同影响能否继续工作。

以核对日的[阿里云 Coding Plan 官方说明](https://help.aliyun.com/en/model-studio/coding-plan)为例，Pro 页面列出每月 200 元、每 5 小时最多 6,000 次请求、每周 45,000 次、每月 90,000 次等限制，并列明支持的模型与工具。
这些请求额度需要按其服务规则理解，不能直接当作同等数量的用户提问。

[Kimi 会员规则](https://www.kimi.com/help/membership/membership-update-rules)则展示另一种组合：会员多项功能共享按 token 消耗的额度池，Kimi Code 另有使用窗口限制；新旧套餐的周限额规则有所不同。
“滚动 5 小时”指有关时间窗口内的用量限制；短期限制恢复时，月度总量仍按自己的规则计算。

两个案例说明了为什么要查看实际套餐、使用明细和恢复时间。
具体价格、模型与规则会调整，应保存核对日期，并以账号当前适用的官方说明为准。

### 5.5.5 数据流向与训练用途分别确认

接入模型时，还需要知道文件怎样被处理。
资料可以保存在本地，由应用检索出片段后发给远端模型；也可以由本地模型处理，或交给其他外部工具。
数据流向取决于实际配置。

**本地文件存放位置、模型运行位置、数据留存和训练用途，需要分别确认。**
查看具体产品、账号类型、设置与第三方服务政策，才能判断这些内容。

例如，[OpenAI API 数据控制说明](https://developers.openai.com/api/docs/guides/your-data)写明，API 数据默认不用于训练，主动选择共享的情况除外；同时，相关服务可能存在安全日志或应用状态留存。
这说明训练用途与保存期限是需要分开看的规则，也应按服务逐一核对。

科研材料是否允许上传，还要符合项目与机构的要求。
选择工具时，把能读取哪些目录、会向哪里发送内容、哪些操作需要确认一起了解，有助于在合适范围内使用。

## 5.6 本章小结

1. **今天常见的 LLM Agent 是 Model 与 Harness 的结合。** 模型处理信息、判断行动，运行框架连接工具、组织执行并反馈结果。使用者需要说清资料、边界和完成标准，再检查实际操作与产物。
2. **RAG 为回答提供外部材料。** 资料是否相关、是否完整，以及回答是否得到证据支持，需要分别检查；科研结果尤其要保留对象、单位、条件和来源位置。
3. **Skill 保存可复用的专业方法。** 先把一次任务做好，再提炼用途、步骤、参考、输出与失败处理，并用新材料试用和修订。
4. **模型、服务平台与产品承担不同作用。** 比较工具时，记录具体版本与配置，用同一真实任务检查读取、执行、专业处理、耗时和费用。
5. **API 连接应用与服务，套餐决定使用条件。** 地址、密钥与模型标识要匹配；用户一次提问可能对应多次调用，额度规则要结合实际用量理解。
6. **自动执行与科研判断需要配合。** 系统可以承担检索、整理、检查和代码运行，研究者负责确定问题、方法和标准，并核验关键结论与结果。
