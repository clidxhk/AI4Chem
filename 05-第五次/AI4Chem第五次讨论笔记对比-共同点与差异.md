## 二、共同点：五份笔记已经建立了哪些基础认识

### 1. 变化的主线是"谁来执行任务、交付什么"

五人都把发展史落在这条主线上，写法不同但结论一致：

- **李冲**分对话、工具调用、Agent 系统三阶段，指出 Agent 系统实现"跨步骤、长时间、带状态的任务闭环"，同时保留"上下文膨胀、错误累加、安全与权限风险"的提醒；
- **杨涵**提炼为三个变化：交付单位从"一轮回答"变成"一个任务"，人从"写提示词"变成"定目标、给边界、审结果"，瓶颈从"模型会不会"变成"上下文够不够、工具全不全、结果验不验得了"；
- **袁桂萍**从"尝鲜期一问一答"讲到"Agent 化与长任务流"；
- **迪力**用六维对照表（人的动作、模型能做什么、谁控制流程、上下文从哪来、交付物、失败模式）支撑同一结论："人退到定目标、设边界、做验收的位置上"；
- **吴冬**用同一个任务对比普通聊天与 Agent 的做法：前者给模板或按贴出的文字作答，后者读文件、找段落、整理表格、标出处、生成文件、缺内容再补查。

大家也都同意提示词工程没有过时：吴冬明确写了"有了 Agent，这种清楚的交代仍然重要"。

### 2. RAG 是"先取资料再作答"，出处必须能回查

五人对 RAG 的定义一致：检索外部资料、连同问题交给模型作答，以减少幻觉、弥补知识截止、利用私有资料；常见的 RAG 不需要重新训练模型。资料来源三通道（知识库、联网搜索、本地文件）在吴冬、杨涵、迪力、袁桂萍四份笔记中都有覆盖，迪力还补了经 MCP 接入专业数据源（文献管理器、代码仓库等）的第四条路径。

核查方面，五人的共同底线是**可追溯**：逐条标注出处（文件名＋页码或 DOI）、关键内容多源交叉、引用回查原文。吴冬的三个追问最便于操作："你是从哪里看到的？原文哪一句或哪张图支持这句话？条件是否一样？"，并提醒"有引用不代表一定正确，它可能引用了不相关的段落，也可能把原文意思说大了"。

### 3. Skills 是把"稳定做法"存下来复用，与临时提示词有本质区别

五人都按题面对比了 Skills 与提示词，共识包括：Skill 常驻可复用、可版本管理、按需加载（李冲"默认只读取元数据，任务触发时才加载具体步骤"；迪力展开为渐进式披露的三层加载）、可在团队间共享（李冲、迪力）。各自给出的科研封装设想：

| 作者 | 封装的任务 | 规程要素的完整程度 |
|---|---|---|
| 李冲 | 论文手稿的文献格式、图片编号检查 | 一句话设想，未展开 |
| 杨涵 | 文献综述与引用核验 | 拆检索式 → 检索去重 → 主题聚类 → 结论回标页码 → 带引用初稿与核验表（标注每条结论有几个来源） |
| 袁桂萍 | 光动力细胞毒性实验 SOP | 加样方法、光照时间与功率、后处理孵育时间、后续表征方法 |
| 迪力 | AIE 文献日跟踪与卡片推送 | 触发、流程、硬性规则、脚本、参考、失败处理、验收七要素俱全 |
| 吴冬 | 论文前言阅读笔记 | 固定五问、保留化合物编号与图号、来源标注、区分作者观点与自己理解、读不清处不猜测，并写明何时需要调整流程 |

共同方向是把"什么算合格"的判断标准固化下来。迪力的表述最直接："提示词每次都要重新说一遍标准，而说漏一条，模型就会安静地把不合格的文献推给你。"

### 4. 模型与产品要分层认识，不排座次

吴冬用"发动机与汽车"作比，并提醒"模型很强，不代表某个产品一定具备读文件、联网或执行代码的权限"；迪力说"壳与脑子可以分开挑"，并明确"差异在定位，不在排名"，选型逻辑是"先明确目标，再选模型，跟我们选机器学习模型是同一个道理"；杨涵逐家给出"主场"。五份笔记对七个国产模型家族的定位描述大体一致：DeepSeek 性价比与开源、Qwen 家族全、Kimi 长上下文、GLM 编程与学术、Doubao 低成本 C 端、MiniMax 语音视频、MiMo 端侧，且都没有给出"谁第一"的排名。

### 5. API 是程序调用模型的接口，三种付费方式分工不同

概念部分五人一致：API 把模型服务封装成程序可调用的标准接口（HTTP 请求、JSON 返回）；API Key 是身份凭证，兼具身份、计费与权限三种作用，必须保密（杨涵"泄露等于别人花你的钱"；迪力给出三条硬纪律：不进代码与 Git、不分享、定期轮换）；订阅买"人的使用权"、API 按量弹性、Coding Plan 固定月费限定工具。

五人还共同触及"一次提问不等于一次调用/一次消耗"：吴冬用打印店类比（印一页与印一本书不能都按"一次"算），迪力给出量级（简单任务约 5–10 次模型调用，复杂任务 10–30 次以上），这是理解各类套餐额度最容易出错的地方。

## 三、主要差异：相同问题，各自往哪里多走了一步

### 1. 发展史：编年、提炼、维度展开还是教学对比

**李冲**的时间线事件最密（Dify、Function Calling、MCP、o1、DeepSeek-R1、Claude Code、Manus、Claude 桌面端、Skills 开放为跨平台标准、OpenClaw、Harness Engineering），适合当"年表"查。**迪力**的时间线事件较少，但多了两层：三阶段六维对照表，以及"2026 年的瓶颈是信任"的判断——各家比拼的不再是生成速度，而是输出能否被验证（沙箱隔离、测试闭环、可审查的 PR），"快不等于可信，能被检验才可信"。**杨涵**几乎不列事件，直接给三个"变了什么"。**袁桂萍**从四个维度展开（问答→工作流、纯文本→多模态、通用→垂直集成、依赖提示词→长上下文＋RAG），覆盖最宽，但后三个维度偏离了"任务执行方式"这一问的主线。**吴冬**先辨析 LLM、ChatBot、Agent 三个词（大脑与手的类比，并声明类比不表示 AI 真正理解一切），再用同一任务对比，最便于入门者建立直观区别。

**整理提示**：编年条目各家取舍不同，引用具体日期（如 OpenClaw、Skills 开放为标准的时间）时宜回到原始出处核对；迪力关于开发者信任度的调研数字未注来源，保留为讨论观点。

### 2. RAG 与核查：操作型、工程型与体系型

| 作者 | 核查思路 | 特点 |
|---|---|---|
| 吴冬 | 三个追问＋人抽查原文 | 操作型：面向使用者的检查动作，落脚"证据不够时写'目前无法确认'" |
| 杨涵 | 逐条标注来源＋关键数字多源交叉＋核验表 | 简明型：把核查做成输出格式的一部分 |
| 迪力 | Agentic RAG 四步检查（该不该查、查到的能不能用、证据够不够、回答有没有被支持） | 工程型：含 Self-RAG/CRAG 思路，标准是"不能自信地说'我不知道'就不该上生产" |
| 袁桂萍 | 引用绑定与元数据追踪、交叉验证、Worker/Critic 互审、沙盒确定性验证、LLM-as-a-Judge、NLI 蕴含检验 | 体系型：系统层机制最全，但未落到自己的科研例子 |
| 李冲 | （第二问后半未写完） | —— |

最值得展开的分歧是：**核查主要靠人抽查，还是靠系统化的自动机制？** 吴冬把最终责任留给人（"重要结论仍要抽查原文"），袁桂萍和迪力描述多层自动核查。两者实为互补：自动机制降低漏检概率，人抽查关键结论仍是最后一道关口。迪力还把这个问题拉回自己的研究：AIE 领域的量子产率、增强倍数、IC50 高度依赖测试条件，要求"结论必须与条件同召回（溶剂、浓度、激发波长、仪器），每条结论必须能回溯到 DOI"——这一条可以直接用于本组后续的文献建库。

### 3. Skills：从一句话设想到完整规程

机制理解上，**迪力**最深：渐进式披露的三层加载与上下文成本（装几十个 Skill 每次调用开销仍小）、确定性步骤交给脚本、失败处理（检索接口不可用就报错不伪造、命中不足按实际数量推送不凑数）。**吴冬**最务实："初学者先把自己认可的做法写清楚，比记住文件格式更重要"，并提醒 Skill 本身也要检查（"规程可能有问题，执行也可能出错"）。**袁桂萍**把 Skills 放进五种复用机制的谱系（提示词模板 → 技能与工具 → 知识库与 RAG → 工作流编排与多 Agent → 记忆与微调），谱系最宽；需要留意的是，题面所指的 Skills（SKILL.md 规范，见吴冬引注的 [Agent Skills Specification](https://agentskills.io/specification)）是这个谱系中的一种具体机制，两者在现场最好区分口径。

例子完整度差异明显（见第二节第 3 部分表格）：迪力的文献日跟踪七要素俱全，可直接当作全组写第一个 Skill 的模板；吴冬补了"何时不适用"（综述、没有图 1、前言缺页要调整流程，不能机械套用）；袁桂萍给出唯一的湿实验视角；李冲的设想最简。**整理提示**：五人例子里文献类占三个、实验类一个、格式检查类一个，现场互评时正好覆盖不同类型。

### 4. 市场：所选产品的分布与一处已核实的事实分歧

五人选择的介绍对象：李冲、袁桂萍选 **DeepSeek Harness**，杨涵、吴冬选 **Kimi Code**，迪力选 **WorkBuddy**。

- **Kimi Code 两份介绍互补**：杨涵讲能力（先分析整个仓库再出 Plan、批准后才动文件、/swarm 多 Agent 并行、HighSpeed 提速），吴冬讲形态（桌面端、命令行、编辑器扩展）与科研用法（读一批光谱表格、写作图脚本、运行后交付图片与汇总表），并给出比较产品的方法：让它们做同一个小任务，看谁漏项少、改动少、费用合适。
- **WorkBuddy**：迪力讲清了它与编程 IDE 路线的差别（桌面原生办公智能体）、Ask/Plan/Craft 三种模式按风险分级"把确认权留给人"，以及个人体会——能读本地文件（实验记录本成了资料源）、能定时跑（文献跟踪自动化）、能挂技能（合格文献的标准被固化复用）。
- **DeepSeek Harness 的分歧（本次最需要澄清的事实点）**：李冲介绍其"一切皆插件"架构（模型适配器、工具注册表、会话存储、沙箱权限、Agent 循环、UI 全部解耦为插件），袁桂萍给出 Agent = Model + Harness 公式与"官方开源 Agent 运行时"的定位；迪力则存疑，认为 harness 在行业语境中是"包裹模型的工程骨架"这一架构概念，"公开资料中未见 DeepSeek 有以此命名的独立产品形态"。

**整理时核实结果**：DeepSeek Harness 确为 DeepSeek 官方产品，[官方页面](https://www.deepseek.com/zh/harness)显示其于 2026 年 7 月底随 DeepSeek-V4-Flash 推出、8 月开源（[GitHub 仓库](https://github.com/deepseek-ai/deepseek-harness)），现处于开发者预览阶段，定位介于"裸 API 调用"与"完整编程 Agent 产品"之间的智能体运行时，官方描述正是"一切皆插件"（模型、工具、存储、权限和 Agent Loop 都可作为插件组合替换）。因此李冲、袁桂萍的介绍有官方依据，迪力的存疑结论需要更新；但他"以官方发布为准"的核验态度正是本次主题（依据核查）的示范，产品形态细节仍应以官方页面为准。

**整理提示**：袁桂萍第四问的家族介绍中并列了 Kimi 探索版、AutoGLM/GLM-Agent 等 Agent 产品，模型层与产品层有交叉，建议按吴冬"发动机/汽车"先分层再介绍。

### 5. 接入与付费：五家案例恰好覆盖三种方式

概念部分五人一致（见第二节第 5 部分），套餐案例五人各选一家，正好拼出全景：

| 作者 | 所查服务商与方式 | 写得最细的地方 |
|---|---|---|
| 杨涵 | 智谱 GLM Coding Plan（订阅） | 积分公式（输入 ×6.9＋缓存命中 ×1.7＋输出 ×24）÷10000、非高峰按 50% 抵扣、支持 ZCode 等 20 余款工具 |
| 迪力 | 阿里云百炼 Coding Plan（订阅） | 模型白名单"版本号逐字符匹配"、三重上限（5 小时/周/月）、按模型调用次数计、5 小时额度每分钟滚动恢复；横向比较腾讯云与天翼云 |
| 吴冬 | Kimi 会员（订阅） | 新旧套餐区别（新套餐滚动 5 小时无周限额）、多项功能共享月度额度、滚动 5 小时的三种常见误解 |
| 李冲 | OpenAI（订阅） | 5 小时滚动窗口＋周限制，Free 到 Pro 500 的档位价格 |
| 袁桂萍 | DeepSeek API（按量付费） | 百万 token 阶梯计价、缓存命中大幅折扣、峰谷定价（夜间半价）、联网搜索按成功请求计费 |

两条最值得吸收的提醒：迪力的比价方法——"各家换算口径不同，比价时要换算到'每次真实提问成本'这个共同单位"（并示范了换算：每月 9 万次调用按复杂任务 10–30 次调用一问，约对应几千次真实提问）；吴冬的边界意识——公开帮助页没有适用于所有档位的统一固定提问次数，"不能直接换算成每月能读多少篇论文"。

**整理提示**：李冲"API 按量付费价格极高、Coding Plan 价格极低"是相对判断的绝对化表述——API 单价并不必然高（DeepSeek 等单价很低），长上下文与 Agent 循环高频调用才会显著累积费用；Coding Plan 在高频编程场景下单位成本通常更低，但仅限授权工具内使用、超出额度另计。迪力"风险由谁承担"的框架（按量付费成本风险自担，订阅与 Coding Plan 转移给厂商、代价是接受使用限制）更适合作为比较基础。

## 五、整体观察与后续建议

### 1. 五人的贡献形成了互补

- **李冲**提供事件最全的编年时间线，把产品史与执行方式的变化连成一条线，适合作为全组的时间参照。
- **杨涵**把五问压得最精炼，三个"变了什么"可直接用作讲义小结；套餐数字与积分公式最完整。
- **袁桂萍**给出机制全景，从检索路由到 NLI 检验再到微调，让小组看到概念背后的系统做法；光动力 SOP 是唯一湿实验 Skill 例子。
- **迪力**贡献了工程细节（渐进式披露、Agentic RAG、额度换算）与一手使用体会，并示范了"存疑就核验"的态度。
- **吴冬**保持入门视角，类比、边界提醒、官方来源与"一起聊"问题齐全，可直接用于现场引导。

与前几次相比，本次笔记的一手使用经验明显增多（迪力的 WorkBuddy 文献跟踪、吴冬对 Kimi 额度的逐条辨析），讨论可以从概念对齐推进到经验交换。迪力的收束句值得作为全组的选型原则："选择的关键从来不是哪个更强，而是哪个在你的场景里可被检验、可被负担、可被复现。"

### 2. 下一次值得一起完成的事

**后续建议**（不视为已布置的任务）：
